# QTranslate 修正專案 —— 交接紀錄

寫給接手這個問題的另一個 Claude Code 對話（或未來的自己）。目的：**在使用者
實際回報問題的那台電腦上**，接續診斷「安裝完設定套用不上／單擊 Ctrl 誤觸發
畫面翻譯」這個還沒解決的問題，不用重新從頭摸索。

---

## 0. 先讀這個：目前的真實狀態

**問題還沒解決。** 這份文件記錄的是好幾輪嘗試與修正，其中大多數已經用嚴謹
的方式驗證過「程式碼邏輯本身是對的」，但**沒有一次是在真正會出問題的機器上
驗證過**——因為到目前為止所有開發與測試都在同一台電腦（下面稱「開發機」）
上進行，而這台開發機從頭到尾都是正常的，從未重現過使用者回報的症狀。

使用者在**至少三台不同電腦**上都回報過類似問題，最新一次（v6.10.7 之後）
仍然回報「還是不行」。這代表：

- 要嘛是還沒真正修到根因
- 要嘛是版本沒更新到（每次都要先確認 exe 版本號）
- 要嘛是另一個完全不同、還沒被診斷出來的成因

**不要重複同一種「我在開發機上驗證過，所以應該沒問題」的推論方式。**
這種推論已經做過好幾輪、每次都被使用者的實測結果推翻。這次需要的是**在
真正出問題的那台電腦上直接蒐證**，而不是在別的地方驗證邏輯。

使用者對回報品質的要求非常明確，請直接遵守：
> 「你多次確認真的沒問題且可行在回報我，不要急著回報，確認真正有達成需求
> 最重要，總比你在那邊瞎忙還說自己搞定了還好。」
> 「有問題就上網找解法，不要自己在這邊瞎忙。」
> 「回答我問題不要廢話」（追問技術問題時要直接、精簡，不要長篇大論）

## 1. 專案是什麼

修好 QTranslate 6.10.0（QuestSoft 出的免費翻譯軟體，Delphi/C++Builder 寫的，
2022 年建置，2022 年後翻譯功能失效）的翻譯功能，並且做成可以在使用者多台
電腦上重複部署的安裝檔。

- **GitHub repo（私有）**：<https://github.com/hj110b13-Andy/QTranslate>
- **最新安裝檔下載**：<https://github.com/hj110b13-Andy/QTranslate/releases/latest/download/QTranslate-Setup.exe>
- **本機工作目錄**：`d:\Claude\qtranslate改良版`（開發機路徑，其他電腦上路徑會不同）
- 目前版本：**v6.10.7**（`349677d`）

### 這套東西實際上是什麼

1. `patch/Google Translate/Service.js` —— QTranslate 的翻譯服務是外部 JS 檔，
   不是編譯進 exe。改連 `clients5.google.com` 端點（原本 `translate.google.com`
   的端點已被 Google 封鎖），並且在送出翻譯前重建被硬換行打散的段落與標題
   （PDF/OCR 文字常見問題）。**這部分已經穩定、沒有已知問題。**
2. `installer/` —— C# WinForms 寫的安裝程式（`net9.0-windows`），把
   QTranslate 原始程式 + 修正後的 `Service.js` 打包成單一 exe，並且負責寫入
   使用者設定（`Options.json`）、快速鍵、滑鼠模式等。**這部分就是目前卡住的
   地方。**
3. `Diagnose.cmd` + `Diagnose.ps1` —— 獨立的診斷工具，設計成不需要系統管理員
   權限即可執行，檢查設定檔內容、提權狀態、多重安裝等。**上一輪使用者回報
   這個工具在某台機器上「沒有東西」（不確定是完全沒反應、有視窗但空白、還是
   沒產生報告檔），這件事沒有查清楚就被使用者打斷對話，是接下來優先要查的
   事情之一。**

## 2. 核心待解問題

使用者在其他電腦上重複回報的症狀（多次、多台電腦）：

1. **裝完之後，選項裡的設定沒有套用**（例如滑鼠模式沒開啟）
2. **單擊 Ctrl 會觸發畫面框選翻譯**，不是預期的「連點兩下 Ctrl」或
   （v6.10.7 之後）「Ctrl+Shift+S」

這兩個症狀先前被當成同一個問題處理，但後來發現**很可能是兩個完全獨立的
成因**：

### 成因 A（已修正，但未在真正故障的機器上驗證過）：安裝時的提權身分問題

**已用 Microsoft 官方 Q&A 文件確認**：當一台電腦的日常帳號不是系統管理員，
UAC 提權時輸入的是**另一個**管理員帳號的密碼，那麼提權後的整個程序都在跑
那個管理員帳號的身分。如果安裝程式在那個身分底下寫 `Options.json`
（`Environment.SpecialFolder.ApplicationData`），寫的其實是那個管理員帳號的
`%APPDATA%`，不是使用者實際登入、實際在用 QTranslate 的那個帳號。

**修正方式的演進**：
- v6.10.6：安裝程式本身不再整支要求提權（`app.manifest` 改成
  `asInvoker`），只有「放檔案進安裝目錄」這一步在需要時才另外提權執行
  （見下方 `Deployer.cs` 說明），其餘操作（`Options.json`、快速鍵、捷徑）
  都在未提權的父程序裡執行。
- v6.10.7：更進一步，**把整個提權需求從結構上拿掉**——預設安裝位置改成
  `%LocalAppData%\QTranslate`（一般使用者本來就有寫入權限，不需要提權），
  解除安裝的登錄機碼也從 `HKEY_LOCAL_MACHINE` 改成 `HKEY_CURRENT_USER`
  （兩者都不需要系統管理員權限，且 `HKCU\...\Uninstall` 是文件記載、
  Windows 原生支援、會正常顯示在「應用程式與功能」的機制）。
  預設情況下整個安裝流程完全不會跳 UAC。

**驗證方式**：在開發機上把 `Options.json` 移走模擬全新機器，直接呼叫真正的
`Deployer.Install()`（不是隔離的單元測試，是安裝程式「安裝」按鈕實際會執行
的方法），寫入這台機器真正的 `%APPDATA%` 路徑與登錄檔，逐項核對寫出來的
檔案內容與 `HKCU`/`HKLM` 登錄機碼位置。**結果正確**：`MouseMode:1`、
`MouseModeOn:true`、`EnableMouseModeOnCtrl:true`、`HotKeyTextRecognition:1619`、
HKCU 機碼存在且內容正確、HKLM 沒有多出我們自己的機碼。

**但這個驗證的侷限**：開發機本身從來沒有出現過「設定套用不上」的症狀，所以
這個測試只能證明「在一台原本就正常的機器上，程式碼邏輯是對的」，**無法
證明「在真正會出問題的機器上，這個修正真的解決了問題」**。使用者在
v6.10.7 之後仍然回報失敗，代表：
- 這個修正可能還是不夠（例如那台機器有更特殊的環境限制），或
- 那台機器測的根本不是 v6.10.7（版本快取、下載到舊版），或
- 是完全不同的第三種成因

### 成因 B（v6.10.7 已改用不同機制迴避，同樣未在真正故障的機器上驗證過）：單擊 Ctrl 誤觸發

**根因**：QTranslate.exe（原廠編譯的執行檔，我們從未修改過這個檔案本體，
只改它旁邊的 `Service.js`）把「連點兩下 Ctrl」註冊成
`RegisterHotKey(MOD_CONTROL, vk=0)`——純修飾鍵、沒有實體按鍵——靠它自己的
內部計時邏輯判斷是不是第二次按壓。這段計時邏輯在**部分機器上**不可靠，
會讓單擊 Ctrl 就直接觸發。**這是原廠程式本體的錯誤，不是我們的設定檔或
安裝程式的問題**，理論上就算設定檔裡存的值完全正確，這個 bug 依然可能發生。

**曾經嘗試過的失敗修法**：另一個獨立的 Claude Code 對話（在使用者的另一台
電腦上，git 作者顯示為 `andy1 <123@gmail.com>`）曾經寫過 `ExePatcher.cs`，
直接對 `QTranslate.exe` 做二進位修補——用 SHA256 鎖定只對已知版本
（`F35A3BC8E09E217130FF97EFE85BA02BD86573B2E0796B003526604454338227`，
6.10.0.0，2022-02-09 建置）動手，關閉 ASLR、在 `WM_HOTKEY` 分派處插入
500ms 雙擊時間判定。**這支修補實測會讓雙擊本身完全失效**（用 `SendInput`
模擬雙擊，修補後不再觸發任何反應），被判定為失敗品，已從主線 git 歷史移除
（v6.10.4 標籤與對應的 GitHub Release 已刪除，v6.10.5 直接接續 v6.10.3，
跳過 v6.10.4 這個編號避免混淆）。**如果要重新嘗試二進位修補這條路，這個
教訓要記住：修補完一定要實測雙擊還能不能用，不能只測單擊不誤觸發。**

**v6.10.7 的做法（迴避而非修補）**：參考另一個獨立、正當的開源 QTranslate
重製版（<https://github.com/ahatem/QTranslate>，Kotlin 寫的，MPL 2.0 授權，
與我們這套完全無關，只是剛好同名）。查看它的執行紀錄發現它完全不使用任何
連點手勢，所有全域快速鍵都是一般的修飾鍵＋按鍵組合（`Ctrl+Q`、`Ctrl+E`、
`Ctrl+I` 等）。**把畫面框選翻譯的快速鍵從「連點兩下 Ctrl」（`0x8200` =
33280）改成「Ctrl+Shift+S」（`0x0653` = 1619）。** Windows 的 `RegisterHotKey`
在有實體按鍵的情況下，只有三個鍵同時按下才會觸發 `WM_HOTKEY`，不需要應用
程式自己做任何計時判斷，結構上不會有「單擊誤觸發」這個失敗模式。

**這是一個真正的行為改變，已經在 README 跟 Release 說明裡明講**：如果使用者
已經習慣連點兩下 Ctrl，這個手感會消失。

**同樣，這個修法從未在真正出現過「單擊 Ctrl 誤觸發」症狀的機器上驗證過**，
因為開發機從來沒有重現過這個 bug（在開發機上，連點兩下原本就正常運作，
單擊原本就沒有反應）。

## 4. 已驗證 / 未驗證，請不要混淆

### 已經用嚴謹方式驗證過的（在開發機上）

- `Service.js` 的翻譯與斷句邏輯：長期穩定使用，無已知問題
- 安裝程式的檔案打包、解壓縮、版本號：`dist/QTranslate-Setup.exe` 與
  GitHub Release 上的檔案逐位元組雜湊值核對一致
- `Deployer.Install()` 這個方法本身：在開發機上模擬全新機器（移走
  `Options.json`），直接呼叫這個方法寫入真正的 `%APPDATA%` 路徑，寫出來的
  檔案內容全部正確
- `NeedsElevation()` 判斷邏輯：在確認開發機的測試程序本身沒有系統管理員
  權限的前提下，對 Program Files 正確判斷需要提權、對可寫入資料夾正確
  判斷不需要
- HKCU 登錄機碼寫入：實測會正確出現在 `HKEY_CURRENT_USER\...\Uninstall\
  QTranslate-Fixed`，且 `HKEY_LOCAL_MACHINE` 沒有多出我們自己的機碼
- 自動化測試套件（`instest/Harness.cs`，50 項左右）：涵蓋設定檔覆蓋/合併
  邏輯、提權判斷、檔案搬移等，全數通過

### 完全沒有驗證過的（因為開發機無法重現症狀）

- **v6.10.6/v6.10.7 是否真的解決了「另一台電腦設定套用不上」的問題**——
  只驗證過「邏輯是對的」，沒有在真正故障的機器上驗證過「結果是對的」
- **v6.10.7 的 Ctrl+Shift+S 是否真的解決了「單擊 Ctrl 誤觸發」**——同上，
  開發機從未重現過這個 bug，無從驗證
- 使用者回報失敗時，**那台電腦當下實際安裝的版本號**是否真的是最新版
  （版本快取、下載到舊版的可能性從未被排除）
- 使用者那幾台故障的電腦，**環境上跟開發機有什麼不同**（防毒軟體、
  OneDrive/雲端同步是否接管了 `%APPDATA%` 或 `%LocalAppData%`、是否為
  網域帳號、Group Policy 漫遊設定檔等）——這些完全沒有資料
- `Diagnose.cmd`/`Diagnose.ps1` 在故障機器上執行時，**「沒有東西」具體指的
  是什麼**（腳本完全沒反應？視窗一閃即逝？沒有產生報告檔？報告檔是空的？）
  ——這個問題被問出去之後，對話被使用者的下一句話打斷，從未得到答案

## 5. 接手後的優先順序建議

**不要重複「在開發機上驗證邏輯正確」這件事**——這個套路已經做了三輪
（v6.10.5、v6.10.6、v6.10.7 各一輪），每次都被使用者的實測推翻。開發機
的驗證能排除「程式碼有明顯邏輯錯誤」，但排除不了「這台特定機器的環境
問題」。

如果這份文件是在**使用者實際回報問題的那台電腦**上被讀到，建議順序：

1. **確認實際安裝的版本**：右鍵 `QTranslate-Setup.exe`（或已安裝的
   `QTranslate-Setup.exe`，通常在安裝目錄底下）→ 內容 → 詳細資料 → 檔案
   版本，確認是不是 `6.10.7.0`。如果不是，先更新到最新版再往下查，
   避免查了半天結果是在查一個已經修過的舊版本。

2. **直接讀取這台電腦的 `%APPDATA%\QTranslate\Options.json`**，不要透過
   `Diagnose.cmd` 間接看，直接用文字編輯器打開，核對：
   - `HotKeyTextRecognition` 是不是 `1619`（v6.10.7 的新預設值，Ctrl+Shift+S）
   - `MouseMode` 是不是 `1`、`MouseModeOn` 是不是 `true`
   - 如果這些值本身就是錯的 → 回到成因 A，安裝程式的寫入邏輯在**這台**
     機器上有問題，需要查為什麼（值錯 vs. 檔案根本沒被安裝程式寫過，例如
     UAC 被使用者取消、或安裝程式中途拋出例外）
   - 如果這些值是對的，但實際操作起來還是單擊 Ctrl 誤觸發 → 那是成因 B
     還沒解決，或是**第三種、完全未知的成因**（例如 QTranslate.exe 本身
     沒有正確讀取這個設定檔）

3. **查清楚 `Diagnose.cmd` 在這台機器上到底發生了什麼**。如果它連跑都跑
   不起來，那本身就是重要線索（PowerShell 執行原則被鎖、防毒軟體攔截、
   `.NET`/PowerShell 版本問題等），需要先解決診斷工具本身能不能跑，才有
   辦法用它蒐集後續資料。

4. **確認這台電腦是否為網域帳號、是否有 Group Policy 漫遊設定檔、
   `%APPDATA%`/`%LocalAppData%` 是否被 OneDrive 的「已知資料夾移動」
   接管、是否有防毒軟體對這類寫入行為做即時攔截**。這些是開發機完全沒有
   的環境變因，從未被排除過。

5. **如果 Options.json 的值本身是對的，但行為還是錯的**，那要往下懷疑
   QTranslate.exe 本體的問題（成因 B 的更深層版本，或全新的第四種成因），
   這時候才需要考慮回到二進位修補這條路——但務必記住第 2 節提到的教訓：
   修補完一定要用 `SendInput` 之類的方式實測「原本該正常的功能有沒有被
   連帶弄壞」，不能只驗證「壞掉的功能被修好了」。

**在得到這台機器的第一手資料之前，不要對使用者做任何「應該修好了」的
宣稱。** 先蒐證，再動手，動手之後再三確認，最後才回報。

## 6. 關鍵技術細節速查

### 快速鍵編碼

QTranslate 把快速鍵存成 `(修飾鍵 << 8) | 虛擬鍵碼`。修飾鍵位元：
Alt=1、Ctrl=2、Shift=4、Win=8；`0x80` 代表「連點兩下」（僅適用於純
修飾鍵、沒有虛擬鍵碼的組合）。

| 名稱 | 值 | 說明 |
| --- | --- | --- |
| `HotKeyTextRecognition` | `1619` (`0x0653`) | Ctrl+Shift+S，畫面框選翻譯（v6.10.7 起）|

### 登錄機碼

- **我們自己的解除安裝項目**：`HKEY_CURRENT_USER\SOFTWARE\Microsoft\
  Windows\CurrentVersion\Uninstall\QTranslate-Fixed`（v6.10.7 起，之前是
  `HKEY_LOCAL_MACHINE` 底下同名機碼，已不再使用）
- **原版 QuestSoft 安裝程式的機碼**：
  `HKEY_LOCAL_MACHINE\SOFTWARE\WOW6432Node\Microsoft\Windows\
  CurrentVersion\Uninstall\QTranslate`（32 位元檢視）。我們的安裝程式會
  嘗試移除這個，避免「應用程式與功能」出現重複項目
- **開機自動啟動**：`HKEY_CURRENT_USER\SOFTWARE\Microsoft\Windows\
  CurrentVersion\Run`，值名稱 `QTranslate`

### 設定檔位置

`%APPDATA%\QTranslate\Options.json`（`Environment.SpecialFolder.
ApplicationData`）。這個路徑不會因為安裝位置改變而改變，永遠是「目前
執行這段程式碼的那個身分」的 `%APPDATA%`——這正是成因 A 的核心：如果
執行身分不是使用者本人（提權用了別的帳號），這個路徑就會指向錯誤的地方。

### 安裝程式的架構（`installer/Deployer.cs`）

安裝程式本身（`app.manifest`）宣告 `asInvoker`，**不會**整支自動提權。
只有 `PlaceFiles()` 這個方法在偵測到目標資料夾需要提權時
（`NeedsElevation()`，實際嘗試寫入測試檔判斷，不是憑路徑猜測），才會用
`Verb = "runas"` 重新啟動自己，帶著 `/elevated-move <暫存路徑> <目標路徑>`
參數，只執行「複製檔案＋移除原版登錄機碼」這一步，其餘全部（設定檔、
快速鍵、捷徑、開機啟動、我們自己的登錄機碼）都在原本未提權的父程序
裡完成。解除安裝走一樣的邏輯，`/elevated-remove <目標路徑>`。

預設安裝位置：`QTranslateLocator.DefaultInstallFolder()` →
`%LocalAppData%\QTranslate`。找既有安裝：`QTranslateLocator.Find()`，
依序查環境變數 `QTRANSLATE_DIR`、我們自己的 HKCU 機碼、原版的 HKLM 機碼、
`%LocalAppData%`、`Program Files (x86)`、`Program Files`。

### 這個開發環境的已知怪癖（避免重複踩坑）

- **從背景／工具呼叫的程序，觸發 UAC 提權對話框不會顯示、也沒人能點**。
  試過 `Start-Process -Verb RunAs`、工作排程器的「最高權限」設定，都卡住
  或悄悄失敗。這代表在這個開發環境裡**無法完整測試「真正需要使用者親自
  點擊 UAC」的路徑**，只能驗證到「提權判斷邏輯正確」跟「提權後實際執行的
  程式碼邏輯正確」，無法驗證「提權對話框真的會正常跳出來讓人點」這件事
  本身（不過這個機制本身是 Windows 標準行為，理論上使用者自己雙擊安裝檔
  時不會有這個問題，因為那是真正的前景互動操作，不是背景程序觸發的）
- **Git Credential Manager 對 `git push` 的憑證流程有時會卡在一個沒人能
  互動的畫面**，尤其是 Git LFS 的憑證認證是獨立機制，`http.extraHeader`
  對 `git lfs push` 是已知會被忽略的（GitHub 官方 git-lfs repo 上有相關
  issue）。可靠的繞法：把憑證直接嵌進推送用的 URL（`git credential fill`
  取得帳密，URL-encode 密碼後組成 `https://user:pass@github.com/...`），
  不寫進任何設定檔，用完即棄
- **`Start-Process -Wait -WindowStyle Hidden` 對某些 GUI 程序有已知的
  等待偵測失效問題**（PowerShell 已知瑕疵），程序其實已經執行完成，
  但 `-Wait` 不會回報，看起來像「卡住」。判斷程序是否真的卡住，要看
  實際輸出的檔案跟 CPU 時間，不要只憑指令沒回傳就斷定失敗
- **一個安裝程式的自我提權腳本（早期版本的 `install-fix.ps1`）曾被
  Windows Defender 判定為惡意程式並鎖住**，自我提權模式（`-Verb RunAs`
  重新啟動自己）是常見的惡意軟體特徵，容易被啟發式偵測誤判。現在的做法
  （安裝程式本身不整支提權，只在需要時對特定步驟提權）風險比較低，但
  如果之後又要對這類「自我提權」的機制動手，這件事要記得

## 7. 使用者的標準與偏好（避免重蹈覆轍）

- **不要急著回報「搞定了」**。要多次確認、確認到真的達成需求才回報。
  之前好幾次回報「應該修好了」，結果使用者實測後發現沒用，浪費了使用者
  的時間，使用者對此明確表達過不滿。
- **遇到卡住的狀況，先查文件／已知問題，不要憑感覺一直試錯**。這個習慣
  在這次對話裡多次派上用場（UAC 環境限制、`Start-Process -Wait` 瑕疵、
  git-lfs 憑證問題，都是先查證再動手才找到真正原因，而不是瞎猜）。
- **設定或行為的改變，如果會讓使用者失去原本依賴的功能，要在改之前明講、
  讓使用者自己決定替代方案**，不要埋在一堆變更清單裡一筆帶過。這次改
  「連點兩下 Ctrl」為「Ctrl+Shift+S」已經在 README 跟對話裡明講過。
- **使用者會在多台電腦上開獨立的 Claude Code 對話，處理同一個 GitHub
  repo**。遇到不認得的遠端 commit，先假設是使用者另一台電腦的另一個
  session 做的，去查證（作者、diff、實測），不要假設它一定是對的、也
  不要假設它一定是錯的。上一次真的遇到過這種情況（`andy1` 那個帳號的
  `ExePatcher` commit），查證後發現是壞掉的嘗試，經使用者確認後捨棄。
- **回覆的長度要配合使用者當下的語氣**。使用者情緒比較急、要求直接回答
  時（例如「回答我問題不要廢話」），就給精簡、直接的答案，不要長篇大論；
  一般情況下該解釋的技術細節、該講的取捨還是要講清楚，不要為了簡短而
  省略關鍵資訊。

## 9. 2026-09-02 在故障機器上的實測結果——推翻了成因 B 的整個假設

**這是在真正故障的機器上第一次得到的第一手資料**，結論跟第 2 節「成因 B」的
假設完全不同，請優先參考這一節，不要再照第 2 節的舊假設去修。

### 這次確認的事實（全部在故障機器上實測，不是開發機推論）

1. **成因 A（提權寫錯身分）在這台機器上已經解決**：全新安裝、全程沒有跳出
   UAC、`Options.json` 寫進正確的 `%APPDATA%`、HKCU 機碼正確、原版 HKLM 機碼
   沒有殘留。v6.10.7 的免提權安裝流程在這台機器上驗證通過。

2. **成因 B 的「雙擊 Ctrl 對應文字辨識」這個認知，從一開始就是錯的。**
   QTranslate 主視窗自己的說明寫得明明白白：
   > 連點兩下 Ctrl => 顯示主視窗（並翻譯選取的文字）
   雙擊 Ctrl 對應的官方功能是「**顯示主視窗**」，不是「文字辨識」（畫面框選
   翻譯）。v6.10.7 改的是 `HotKeyTextRecognition`，改錯了目標。

3. **「顯示主視窗」這個功能的熱鍵是寫死在 `QTranslate.exe` 裡的，完全不讀
   `Options.json` 的 `HotKeyMainWindow`，也不讀 QTranslate 自己選項 UI 裡對
   這一項的設定。** 用三種方式都證實了這件事：
   - `Options.json` 裡寫 `HotKeyMainWindow: 849`（Ctrl+Alt+Q），UI 顯示的卻是
     `Double Ctrl`（原廠出廠值），代表沒套用。
   - 直接呼叫 Win32 `RegisterHotKey` 測試，`Ctrl+Alt+Q` 這個組合在系統上完全
     沒被佔用（可以成功註冊），代表 QTranslate.exe **沒有**用這個值去註冊；
     但「純 Ctrl（無實體鍵，`MOD_CONTROL`, `vk=0`）」這個組合**已經被佔用**
     ——就是 QTranslate.exe 自己在用。
   - **在 QTranslate 自己的選項 UI 裡，把「顯示主視窗」那一列的熱鍵直接清空
     （不是改成別的組合，是完全沒有熱鍵），套用後單擊 Ctrl 依然跳出主視窗
     畫面。** 這是最終確認：這個行為不受任何使用者可控的設定管道影響，
     連 QTranslate 自己的選項介面都關不掉。

4. **其他熱鍵（Ctrl+Q 彈出視窗、Ctrl+Shift+Q 辭典、Ctrl+E 朗讀）都正確套用
   了**，`Options.json` 裡的值也確實生效、系統上也確實被 QTranslate 佔用。
   問題只出在「顯示主視窗」這一項，不是整份設定檔讀取失敗。

5. `HotKeyTextRecognition` 改成 `1619`（Ctrl+Shift+S）**看似**有生效
   （`RegisterHotKey` 測試顯示這個組合沒被佔用，UI 上該欄位是空的），但因為
   單擊 Ctrl 觸發的根本是另一個功能（顯示主視窗），所以這個修改對使用者
   實際回報的症狀**毫無幫助**——改對了一個沒人在抱怨的東西。

### 結論：光改設定檔這條路已經走到頭了

「顯示主視窗」綁定純 Ctrl、單擊就誤觸發，這是**寫死在 `QTranslate.exe`
本體裡的行為**，不是設定檔或安裝程式的問題。不管是我們的安裝程式寫
`Options.json`，還是使用者自己在 QTranslate 選項 UI 裡改，都無法改變或
關閉這個行為。這代表：

- 第 2 節「成因 B」描述的修法方向（把 `HotKeyTextRecognition` 改成一般組合
  鍵來迴避雙擊計時 bug）**從根本上就無效**，因為它改的不是真正在響應單擊
  Ctrl 的那個功能。
- 要真正解決，只剩下改 `QTranslate.exe` 本體這條路，也就是回到第 2 節提過
  、已經失敗過一次的二進位修補方案——但這次要修補的目標不同：上次
  `ExePatcher.cs` 修補的假設也是「雙擊 Ctrl 觸發文字辨識」，這次已知那個
  假設是錯的，修補邏輯需要重新針對「顯示主視窗」這個功能對應的程式碼
  路徑，而不是原本假設的文字辨識路徑。
- 上次的教訓一定要記住：**修補完一定要實測雙擊「顯示主視窗」還能不能正常
  使用**，不能只驗證單擊不誤觸發，那次的修補就是因為只驗證了一半而失敗。
- 另一個可能的迴避方案（尚未評估可行性）：寫一個常駐的低階鍵盤鉤子
  （`WH_KEYBOARD_LL`），在按鍵事件送到 QTranslate 之前攔截／吃掉單獨的
  Ctrl 放開事件，阻止 QTranslate 收到它期待的手勢。這條路完全繞開修改
  `QTranslate.exe` 本體，但複雜度與副作用（可能干擾使用者用 Ctrl 做其他
  操作，例如複製貼上快速鍵的修飾鍵狀態）都需要評估，還沒有人嘗試過。

### 追加驗證：「文字辨識」本身沒問題，但發現第三個獨立症狀——設定無法持久化

- **「文字辨識」單獨用 Ctrl+Shift+S 可以正常觸發畫面框選翻譯**。所以
  `HotKeyTextRecognition` 這個熱鍵設定本身是有效的，問題只出在「顯示主
  視窗」共用了寫死的純 Ctrl 系統熱鍵、把它蓋過去了。

- **滑鼠模式在這台機器上也能正常觸發**（選字後彈出翻譯視窗），但使用者
  講了一句關鍵的話：「主要是設定不會儲存，我每次結束重啟都要手動開啟
  滑鼠模式」。這是第三個、獨立於前兩個成因的症狀，很可能才是使用者最
  一開始回報「裝完之後滑鼠模式沒開啟」的真正原因——不是安裝程式寫錯
  （成因 A 已經證實在這台機器上是正常的），而是**使用者自己每次用完
  關閉程式後，手動調整過的設定沒有被存回去，下次開啟又變回舊的狀態**。

- **實測證實**：完整走過「開啟 QTranslate → 在選項對話框修改設定（清空
  熱鍵／切換熱鍵／改滑鼠模式／把顯示主視窗熱鍵改成 Ctrl+Alt+T）→ 按套用
  → 從系統列正常離開程式（不是硬殺、不是當機）」這一連串動作，`Options.
  json` 的檔案最後修改時間**完全沒有變化**，`HotKeyMainWindow` 也還是
  安裝時寫入的舊值 `849`，沒有變成 Ctrl+Alt+T 對應的 `852`。也就是說
  **QTranslate.exe 在正常關閉的流程裡，沒有把使用者在 UI 上做的任何調整
  寫回磁碟**。

- **一度懷疑是第三方防毒軟體攔截寫入**：這台機器裝有 Norton Security
  Ultra，且已經過期超過 3 年沒更新、UI 打不開、標準解除安裝失敗（卸載
  程式引用的 `NGC\...\InstStub.exe` 檔案本身缺失）。用 Norton 官方的
  Remove and Reinstall（NRnR）工具強制清除、控制台清單也手動移除乾淨、
  Windows 安全性中心也不再登記 Norton 了（雖然背景的 `NortonSecurity`
  服務本身沒有真正停掉，這部分移除得不夠徹底）。**但即使控制台清單已經
  清乾淨，重新測試「改設定 → 套用 → 正常關閉」，Options.json 依然完全
  沒有更新。** 這代表 Norton **不是**（至少現有證據不支持是）造成這個
  問題的原因，不需要再往這個方向查——如果要繼續追查，優先度應該放在
  `QTranslate.exe` 本體對這些特定欄位的寫入邏輯，而不是外部軟體干擾。

### 三個症狀，同一種模式

到目前為止，三個獨立確認過的問題（顯示主視窗熱鍵寫死忽略設定值、文字
辨識曾經被顯示主視窗蓋過去、滑鼠模式等設定無法持久化）都指向同一種
模式：**`QTranslate.exe` 對特定欄位的讀取與寫入邏輯本身有缺陷，跟
`Options.json` 檔案內容是否正確、跟安裝程式怎麼寫、跟外部軟體干擾都
無關。** 這已經不是「設定檔沒套用」的問題，而是原廠執行檔本體在處理
這些設定時的行為缺陷。要真正解決，勢必得回到修改 `QTranslate.exe` 本體
這條路（二進位修補），改設定檔這個方向已經被反覆證實走不通。

### 這次沒有查的

- 沒有查清楚為什麼「顯示主視窗」「滑鼠模式」这类欄位的寫入會失敗，但
  「顯示彈出視窗」「顯示辭典」「聆聽選取的文字」這幾個熱鍵卻能正常套用
  ——兩組欄位在 `Options.json` 裡的資料型別、巢狀位置看起來並無不同，
  這個差異的成因還不清楚，值得先查（也許能從這個差異反推出 exe 內部
  對設定的存取邏輯，對後續二進位修補會有幫助）
- Norton 服務本身沒有真正移除乾淨（`NortonSecurity.exe` 仍在背景執行、
  開機自動啟動、安裝目錄還在），如果使用者想徹底清乾淨這套過期軟體，
  可能需要再跑一次 NRnR 或手動處理，但這已經與 QTranslate 診斷無關
